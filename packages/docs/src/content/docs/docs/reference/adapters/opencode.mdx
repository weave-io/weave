## Install

Use the canonical package name:

```text
@weaveio/weave-adapter-opencode
```

The package root is the canonical OpenCode plugin entry. Add it to OpenCode's `opencode.json` or `opencode.jsonc` with an exact version:

```json
{
  "plugin": ["@weaveio/weave-adapter-opencode@<exact-version>"]
}
```

The optional `@weaveio/weave-adapter-opencode/plugin` export is available for integrations that require an explicit plugin subpath. Do not use an older package alias.

## Configure Weave

Create `.weave/config.weave`, then validate it:

```sh
weave init --scope local --yes
weave validate --project
```

OpenCode fetches the plugin package at startup. Restart OpenCode after changing the plugin version or Weave configuration.

## Commands

The adapter registers only prompt-based plan-entry commands through the config hook:

- `/weave:start` to submit a plan-entry prompt to the configured agent.
- `/start-work` as a compatibility alias for `/weave:start`.

It does not register `/weave:run` or deliver live `RuntimeCommandProjection` handlers. The `command-entrypoints` capability is therefore degraded. The adapter also maps Weave agents, model preferences, prompt composition, and supported policy fields to OpenCode's native configuration.

## Provider acceleration is unsupported

An agent's `fast true` is neutral intent. OpenCode's plugin surface can change a request through `chat.params` and `chat.headers`, but its public plugin events and assistant messages expose no correlated official response-body evidence — no OpenAI `service_tier` and no Anthropic `usage.speed` — for a successful call. A successful status, an error payload, or ordinary token usage is not evidence.

The adapter therefore sends no acceleration control and changes no request option or header. The `provider-fast-activation` capability reports `unsupported` with the bounded reason `response-proof-unavailable`. Materialized agent configuration never claims that acceleration was requested or applied.

This is an optional-capability gap. It warns and never blocks descriptor materialization, agent mapping, commands, or lifecycle.

Support can be enabled only after the plugin contract exposes correlated official response-body evidence for the same attempt, proven in a real harness. Mocked unit coverage is not that proof.

## Verify loading

Use OpenCode's own diagnostics:

```sh
opencode debug config
opencode debug info
```

These commands verify the resolved plugin and configuration. See the [support matrix](./) for the boundary between implementation and release status.
