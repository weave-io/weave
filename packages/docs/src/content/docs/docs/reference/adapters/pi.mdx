## Install

The Pi adapter is implemented, but its package is distributed through the nightly channel only. Pi loads the extension through its package installer:

```text
pi install npm:@weaveio/weave-adapter-pi@nightly
```

The adapter requires Pi `>=0.81.1` and runs in the Bun-based Pi environment.

## Activate Weave

Start Pi in a project with a valid `.weave/config.weave`. The extension checks trust, configuration, and capabilities before activation. If those checks cannot pass, it enters **health-only** mode: health and diagnostic commands remain available, but configuration-driven execution is disabled.

Fix the reported configuration or installation issue, then restart Pi to activate the full adapter.

## Switch agents

Use `Alt+A` to cycle through healthy primary agents. The active agent is shown in the Plan Rail as `◆ WEAVE · <AGENT>`, and the rail states the `Alt+A` hint whenever there is another primary to cycle to. Switching changes the active Weave agent without changing the project configuration.

In a session that cannot show a widget, the agent name falls back to a single `weave-agent` status entry instead. That entry carries a background tint chosen deterministically from the background tokens the active theme supports, so one color means one agent in every session. Different agents may share a color. If the theme provides no background support, the entry renders the agent name in accent bold with no tint.

## Commands

The extension exposes these commands:

- `/weave:start` — start configured work.
- `/weave:run` — run a durable workflow.
- `/weave:resume` — resume recorded work.
- `/weave:advance` — advance the active workflow.
- `/weave:abort` — stop active work.
- `/weave:status` — inspect workflow status.
- `/weave:health` — inspect activation health.
- `/weave:plan` — inspect the current plan.
- `/weave:artifact` — inspect an available artifact.

### Start work and run workflows

`/weave:start` is the only plan-execution command. It confirms an existing plan and submits it as one visible foreground Pi turn. It records no durable workflow state.

`/weave:run` does one separate thing: it explicitly starts a named durable workflow that the engine manages and persists. Neither command implies the other, and `/weave:start` never starts a durable workflow on your behalf.

### Track the active task

The **Plan Rail** is the single owner of ambient parent context. It mounts above the Pi editor and states the selected agent and the active plan together:

```
◆ WEAVE · LOOM · Alt+A cycle · pi-child-overlay-ux-feedback
● ● ◐ ○ ○ ○ ○ ○   3/8
┃ now   Child overlay rendering
┗ next  Native child stream rendering
```

The rail degrades through measured terminal widths. It drops the plan name first, then the `next` row, then the word `cycle` from the `Alt+A` hint. The agent name and the active task survive to the narrowest width. It reads parent-side facts only, so it cannot show a child ID, token count, cost, elapsed time, or queue depth.

The plan rows clear when there is nothing active: no tracked workflow, no readable plan task, a completed, failed, or cancelled workflow, or a lookup Weave could not read. The agent row remains while a Weave primary is active. If your session tracks no workflow but Weave finds an eligible recovered pointer, the rail may show that paused plan as read-only state. Continue it with `/weave:resume`; showing it starts nothing.

Press `Alt+T` to open the read-only plan-task list. It reads the same active plan and recovery state as the rail, marks each task `[ ]`, `[~]`, or `[x]`, and opens on the active task. Your configured Pi keybindings drive it: `tui.select.up` and `tui.select.down` scroll, `tui.select.cancel` closes, and the hint line names the keys you actually have bound. The list scrolls and closes; it starts, resumes, advances, and cancels nothing.

When no plan is available or Weave cannot read the plan or workflow, the list reports a short notice instead of opening a stale or empty view.

## Provider acceleration

An agent's `fast true` is neutral intent. The adapter carries it on the active agent and on authenticated child sessions, and turns it into a provider control for one mapping only.

| Mapping | What Pi does |
| --- | --- |
| OpenAI Codex subscription, the ChatGPT-backed `openai-codex` provider | Sends the Codex fast control under the exact rules below |
| Public OpenAI API Fast/Priority, the `openai` provider | Nothing. Reports `unsupported` |
| Every other provider | Nothing. Reports `unsupported` |

These are two different OpenAI contracts. The public API contract stays unsupported on Pi, because Pi's provider header, request, and response hooks cannot prove the effective transport of one prepared request together with that same request's response body. The adapter registers no such hook and writes no `service_tier`, `speed`, or `anthropic-beta` value there.

### When the Codex mapping applies

Weave registers its own `openai-codex` provider that wraps Pi's native one, so it holds the effective transport, the final request, and the same attempt's response. A request is mapped only when all of this is true:

- your active agent declares `fast true`;
- its resolved model is one of the allowlisted Codex models, and the request asks for that same model;
- the request goes to the first-party ChatGPT backend, with no gateway or proxy base URL in `models.json`;
- your credential is a ChatGPT subscription OAuth login;
- nothing else already set a `service_tier` or a Codex routing hint on the request;
- your Pi host is at least `0.83.0`, exposes the codex provider seam, and Weave's registration succeeded in a trusted, non-health-only session or an authenticated Weave child.

A mapped request is sent over SSE and carries both parts of the Codex contract, or neither: `service_tier: "priority"` in the body, plus the `originator` and `x-codex-routing-hint` routing headers.

The window is process-level, because the provider seam has no per-request agent identity. While a fast agent is active, an ambient Pi request on the same allowlisted model, such as a branch summary or a title generation, is mapped too.

### What happens otherwise

No `fast true`, any failed rule, a gateway base URL, an older host, a failed registration, or a conflicting value already on the request: Pi uses its native behavior and your request is byte-identical to the same setup without `fast true`. The one exception is a routing-hint conflict that appears only as the request is sent, after Weave already wrote the tier. Weave cannot take the tier back, so it blocks that request instead of sending a partial control.

### What the states mean

`requested` means Weave sent both controls on that attempt. It does not mean the request was faster. `applied` needs response evidence from the same attempt with the exact value `service_tier: "priority"`.

On Pi 0.84.2 the backend reported `service_tier: "default"`, standard speed, for a mapped request and an untouched control alike, so a successful mapped request ends at `not-confirmed`. `applied` has never been observed. `/weave:status` shows the sanitized state, such as `fast: requested (codex-sub-05, openai-service-tier=absent)`, `fast: not-confirmed (codex-sub-05, openai-service-tier=standard)`, or `fast: unsupported (harness-seam-unavailable)`. `requested` appears as soon as Weave writes both controls, with the evidence outcome still `absent`; the same attempt's response resolves it to a terminal state. Weave never infers acceleration from status, latency, or its own change to the request.

This capability is optional. It warns, never enters health-only mode, and never blocks activation, prompts, models, tools, delegation, or child bootstrap.

## Private children

Pi can run private child agents for delegated work and direct workflow steps. Child sessions inherit the authenticated configuration and count toward the configured parallel-child limit. Finished children release that capacity.

The optional child inspector is adapter-owned and local-only. Its exact `child_inspection` defaults, bounds, private storage path and permissions, controls, commands, quotas, trim markers, clear behavior, recovery scope, resume limits, export boundary, and privacy rules are defined by the repository's [amended Spec 33](https://github.com/weaveio/weave/blob/main/docs/specs/33-spec-pi-adapter/33-spec-pi-adapter.md). [ADR 0013](https://github.com/weaveio/weave/blob/main/docs/adr/0013-pi-private-child-sessions.md) records why this history does not belong to the engine. Private history may contain sensitive raw content; it is not an engine transcript, workflow recovery store, telemetry stream, or exported transcript.

See [Prompts, models, and policy](../../../prompts-models-policy/) for delegation intent and the [support matrix](./) for distribution status.
