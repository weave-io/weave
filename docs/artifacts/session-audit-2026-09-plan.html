Weave Remediation Plan

Weave's job is to let you talk to one agent and get the work of many. In real sessions it lost the most time to failed or badly chosen delegations, to serial execution of plans that could have run in parallel, and to tasks that ran silently for so long they looked stuck. This plan sets measurable goals for each of those problems, describes the fixes, and names the tests that stop them coming back.

Decisions already made

These decisions from the review of the first findings constrain everything below.

Kept

/weave:start stays explicit

Harnesses don't switch the primary agent unless the user does it, so handing a plan to Tapestry through a command stays. This plan doesn't touch that handoff.

Kept

No per-change verification loops

#182 reverted #170 because Shuttle and Tapestry spent hours re-checking their work. Every verification idea here is triggered by a specific event, runs once, and is measured against Shuttle's baseline task duration.

Decided

0.2.0 does not ship

0.2.0-next.0 isn't a stable release. Fixes land on main and ship when you decide they're ready for 0.2.1. No backport, so latest (0.1.2) keeps the category-shuttle bug until then. Dogfooding and the L3 proofs run against local builds of main. If the prerelease is withdrawn, deprecate it and remove the next tag rather than unpublishing (see risks).

Decided

Loom never executes plans

Loom creates plans (via Pattern) and answers questions. Executing a plan belongs to Tapestry alone. If you message Loom while a plan is active, it answers and points you to /weave:start to resume; it never delegates plan tasks itself.

Priority

Delegation accuracy first, with tests

A failed or misrouted delegation wastes both time and tokens. WS1 fixes this first and adds tests at five layers, from unit tests through to data from real sessions.

Priority

Parallelism and "stuck" next

Plans ran serially and long tasks gave no sign of progress. WS2 makes the execution schedule deterministic, so independent tasks run together.

Deferred

No watchdog or time budgets

These are out of scope for now: they can only be built on some harnesses (OpenCode, likely Pi) and not on others (Claude Code, Copilot). Revisit only if "stuck" turns don't fall after WS2.

WS0

Measure what sessions actually do

P0 · prerequisite

This plan is only as good as its numbers. The analysis behind it was a set of one-off scripts, so WS0 turns them into a repeatable tool whose output can be compared across releases.

Goal

A single command that turns a harness's session store into the scorecard above.

Remediation

  1. Add scripts/audit/opencode-sessions.ts (Bun, bun:sqlite, opens the database read-only). It takes a date range and a project filter and outputs a scorecard in both JSON and Markdown.
  2. Each metric uses a documented definition. For example, a "configuration failure" is a task error whose message matches Model not found, Unknown agent type, or a missing subagent_type.
  3. Commit the baseline as a non-normative artifact under docs/artifacts/session-audit/.
  4. Put it under scripts/, not the engine, because reading a harness database is harness-owned (docs/adapter-boundary.md). Readers for Claude Code and Pi can come later.

Done when

Running the audit over 4–18 Sep reproduces the baseline column above, and it has been run at least once on a newer week of sessions.

WS1

Delegation accuracy

P0 · biggest issue

Whenever a delegation fails or goes to the wrong agent, the user pays in turns and waiting. The failures below happened in real sessions and none of them were caught before release.

Evidence

  • All 11 category-shuttle delegations failed instantly. Ten failed with Model not found: claude-sonnet-4-5/. and one tried shuttle-frontend, which doesn't exist.
  • Loom sent 14 tasks to OpenCode's built-in explore and general agents instead of Thread or Shuttle.
  • Four Pattern delegations died with Connection reset by server, and a user had to notice each one.
  • Generic Shuttle received 53% of all delegations, even in repos that define categories for the files being changed.
  • One delegation prompt told Thread to read two files that didn't exist.

Root causes

aBuiltin and category definitions use bare model names. OpenCode reads claude-sonnet-4-5 as a provider with an empty model ID. The fix (b4f8efac) is only on 0.2.0-next.0. bLoom's delegation list is built from config, not from what the harness actually materialized, so an agent that failed to materialize is still offered to Loom. cloom.md mentions shuttle-backend and shuttle-frontend as names to avoid. Naming them in a prohibition is exactly what primes the model to try them. dHarness built-in subagents stay visible alongside Weave's agents. eNothing retries transient failures and nothing falls back after a configuration failure. fGenerated category-shuttle descriptions don't carry the category's file patterns, so Loom can't tell which files a category covers.

Remediation

  1. Keep the model fix on main and ship it with 0.2.1. The provider-qualified model resolution from b4f8efac is already on main. The L1 contract test locks it in so it can't regress before 0.2.1, and the 0.2.1 release notes should say that category shuttles were broken on 0.1.2. (fixes a)
  2. Only offer agents that were actually materialized. The adapter reports which agents it materialized and why any failed. The engine renders delegation.targets from that set alone and logs each exclusion. This follows the boundary rules: the adapter supplies context and the engine returns a result. Record the decision as an ADR. (b)
  3. State the delegation rule positively in loom.md: "Delegate only to the agents listed above." Remove the example names. (c)
  4. Hide harness built-in subagents from Weave's primary agents, using a mechanism verified for each harness: OpenCode's agent disable or task permission, Copilot's disabledSubagents. (d)
  5. Recover within the same turn. A failed delegation comes back to the calling agent as the task's error result, and only that agent can act on it. The adapter can't re-run a task. So this is a rule for Loom and Tapestry: after a transient error such as a connection reset, send the same task once more. After a configuration error, send it to generic shuttle and tell the user in one line which agent is broken. (e)
  6. Give category shuttles routable descriptions: generate them from the category's description plus its patterns, e.g. "handles packages/adapters/**". (f)
  7. Loom never executes plans. The adapter passes plan state (.weave/state.json: active plan, tasks remaining) to Loom as context. Loom's prompt says, positively: "While a plan is active, answer the user and point them to /weave:start to resume; Tapestry executes plan tasks." Loom's delegation list stays as it is, because Loom still does ad-hoc Shuttle work.

WS2

Parallel execution

P0

Plans already declare their dependencies (Depends on) and the files each task touches (Files). Tapestry still runs them one task at a time, because at runtime it has to decide from prose whether tasks are safe to run together, and its prompt says "when in doubt, run sequentially". Running independent tasks together shortens plans directly, and it shortens the stretches of silence that made sessions look stuck.

Evidence

  • The Aside foundation plan had 19 tasks. Task 17 depended only on 3b and tasks 13 and 14 were independent, yet everything ran in sequence for about 2.8 hours before the first parallel batch.
  • Only 30 of 352 Loom delegation steps and 20 of 190 Tapestry steps dispatched more than one task.
  • Shuttle runs reached a p90 of 11.4 min and a maximum of 35 min; "you got stuck" was said 8 times across 6 sessions.

"You keep getting stuck and I'm not sure progress is being made."

Remediation

  1. Compute the schedule deterministically. A pure function computeExecutionWaves(tasks) next to plan-task-parser.ts derives waves from Depends on and Files. Tasks at the same dependency level whose file sets overlap go into consecutive waves. The /weave:start context gives Tapestry the schedule, e.g. "Wave 3: tasks 5, 6, 17". The model no longer judges parallel safety.
  2. Keep waves wide. Pattern puts edits to shared files into small integration tasks and adds an ## Execution Waves preview to each plan. A plan validator warns when a plan with more than 5 tasks has a critical path equal to its task count.
  3. Dispatch a whole wave at once. Tapestry sends every task in a wave in a single turn, up to a concurrency cap from a new execution { max_parallel 3 } settings block. Being a DSL change, it needs schema, validate and parse_config tests, spec and docs, and a website update.
  4. Say what is running. When Tapestry dispatches a wave it names the tasks in one line, and when the wave returns it reports the results in one line. Silence then means work is in progress, not that something died. This is a prompt rule and works on every harness.
  5. Later, only if the audit shows disjoint-file waves are too narrow: execution { isolation worktree } runs tasks that touch the same files in separate git worktrees and merges them after each wave.

Tests

  • Unit tests for computeExecutionWaves, with fixtures taken from the real Aside, madsmenu and harmony plans. Includes a golden test that the Aside plan produces at least 6 waves, not 19.
  • A trajectory eval, tapestry-parallel-waves: a plan with three independent tasks whose file sets don't overlap. The observer must record spawn intervals that overlap in time.

Deferred

Watchdog and time budgets are out of scope for now. Nothing can interrupt a model mid-turn, so a watchdog would have to observe and cancel subagents from outside. That's possible on OpenCode v1 (confirmed in the SDK), likely on OpenCode 2 and Pi, and not possible on Claude Code or Copilot. If the "stuck" metric doesn't fall once waves and wave reporting ship, revisit it.

Done when

Across a week of dogfooded plans, wall-clock time is at most 1.3× the critical path, every multi-task wave was dispatched concurrently, and "stuck" turns are down from the baseline.

WS3

Environment awareness and proportionate verification

P1

#182 showed that blanket verification costs hours. The cheaper failures are still worth fixing: the agent not knowing which tools it has, and a reported bug being called fixed without checking the symptom. Each fix here runs once, is triggered by a specific event, and is checked against Shuttle's duration guardrail.

Evidence

  • You told Loom where gh lives (/usr/bin/gh) in five sessions, and told it about the fly, copilot and podman CLIs and the tokens in ~/.bashrc in others.
  • GitHub Actions URLs were read with webfetch (47 × 404), and Loom asked you to paste logs.
  • In madsmenu the create-family bug went through three rounds of fixes, each reported as passing typecheck and lint, while the symptom was still there.

"No you run it." · "You can do the verification yourself."

Remediation

  1. Give the agent its environment as context. Once per session the adapter checks which CLIs are on PATH (gh, fly, podman, docker, dotnet, bun, copilot), whether gh is authenticated, and the names only of relevant environment variables. The engine renders this as {{environment.*}} template context. Loom's prompt adds: "GitHub URLs are read with gh."
  2. One check when you report a bug. When you report something you observed, the fix is done after a single check that the symptom has gone (a request, a CLI run, or one reproducing test). That check replaces broader test suites, it doesn't add to them.
  3. Verify a plan once. Tapestry runs the plan's Verification section one time at the end and reports any failures to you. It does not re-delegate fixes on its own, which avoids the #170 loop.

Tests

  • Adapter unit test: the environment probe emits variable names and never their values, checked with fake secret variables.
  • L2 prompt contract: {{environment.*}} renders, and falls back cleanly when the adapter supplies nothing.
  • Trajectory case: in a fixture with a gh stub, Loom answers a GitHub Actions URL with gh run view, not webfetch.

Done when

A week of dogfooding produces zero environment reminders from you, GitHub-URL 404s drop to 5 or fewer, and Shuttle's p50 and p90 stay within 20% of baseline.

WS4

Conversation friction

P2 · pick from these

These are options, not commitments. Each is small and independent, and each maps to a scorecard row, so after phase 1 we can pick the ones the audit shows still matter.

A · Proportionate review gates

Warp runs automatically only when the changed files touch security-sensitive code; changes that only touch documentation skip it. Loom's rule "on REJECT, ask the user how to proceed" becomes: fix a within-scope rejection once and re-review, then report; ask only when the fix would change scope. Once you override a gate, that holds for the rest of the session.

Earlier sessions also ran a second, model-variant copy of each reviewer (e.g. weft-github-copilot-claude-opus-5). That came from a review_models setting only in 26 sessions on 5–6 Sep (harmony and agent-evals); no current config has it. Nothing to change unless you turn it back on.

"I don't care about those security issues, I care that the CI for the pull request passes."

B · Finish the outcome you asked for

When you name an outcome, Loom keeps going until it sees that outcome or hits a blocker. "Fix CI" includes pushing and watching the run until it's green. "Commit" means everything in the working tree unless you narrow it, and the reply lists what went in. This targets the 29% of Loom turns that end with an offer and the 41 replies that were just "yes".

C · Plans that explain themselves

When Loom hands over a plan it says, in order: what you'll get, how big it is (tasks, waves, critical path), and which decisions it needs from you. Only then does it point to /weave:start. Mockups, prototypes and questions never go to Pattern.

"Why do you need a plan to show me a mockup?"

D · Question tool resilience

If the question tool errors or is aborted (as it often was in the Fleet UI), Loom asks the same questions again as numbered plain text. Add a worked example in Loom's prompt showing the question key it keeps leaving out, and add an L2 test for it.

E · Less noise in chat

Drop the "2/2 done" footers from chat replies (the sidebar todo list keeps progress). Replace per-delegation narration with WS2's status lines, which only appear while a task is running long.

F · Follow-ups during a plan decided → WS1

Loom never executes plans. The implementation and its eval case are now in WS1 (remediation step 7 and L4).

Roadmap

The phases run in order because each one's exit check depends on the previous one: WS0 has to exist before any target can be measured.

Phase 0 · week 1

Baseline and immediate fixes

WS0 audit script and committed baseline. Dogfooding switched to local builds of main (model fix included); 0.2.1 ships whenever you call it ready. L1 and L2 contract tests. Routing eval baseline.

Exit: stable category shuttles work; CI fails on a bare model or a missing delegation target.

Phase 1 · weeks 2–3

Delegation hardening

Delegation list built only from materialized agents (with ADR), built-in agents hidden, retry and fallback, generated category descriptions, L3 live proof, L4 eval cases.

Exit: WS1 "done when" met on a week of dogfooding.

Phase 2 · weeks 3–5

Parallel waves

computeExecutionWaves, the wave schedule in Tapestry's start context, the execution DSL block, one-line wave reporting, and the parallel-waves trajectory eval.

Exit: plan wall-clock ≤ 1.3× critical path; "stuck" turns down from baseline.

Phase 3 · weeks 5–6

Environment and one-shot verification

Environment probe and template context, the one-check rule for reported bugs, plan verification once at the end.

Exit: zero environment reminders; Shuttle duration within guardrail.

Phase 4 · ongoing

Friction

Re-run the audit, then pick from WS4 by the size of the gap on the scorecard.

Exit: offer-endings ≤ 15%; question-tool failures ≤ 5%.

Documentation per AGENTS.md: a spec for execution waves and the execution block (docs/specs/37-…), an ADR for building the delegation list from materialized agents, an update to docs/adapter-boundary.md for environment context, and tryweave.io pages for the new settings. Each workstream gets a GitHub issue that its PRs reference.
